# Modern Android compatibility — source review, 2026-10-23

Scope: authorized Android ADB diagnostics and read-only Fastboot probing. Product references establish that a phone exists, **not NEXVARY operation support**. No physical handset or Windows USB binding was tested in this increment. iOS, non-Android HarmonyOS, vendor Download/EDL/DA protocols, encrypted-data recovery and model-specific flashing are outside this implementation.

## Implemented behavior

`DeviceCompatibility.hpp` produces a versioned observation map from the existing bounded allowlist. The map separates API family/preview/first API/page size, reported layout, reported boot/encryption/security patch, and actually parsed diagnostic availability. `attestationVerified` and `oemOperationsApproved` remain false; hardware validation remains pending. Unknown future APIs are readable without granting operations. Missing values never become a positive capability or an implicit disabled-security claim. Duplicate allowlisted properties are dropped entirely, rather than choosing a winning identity/API value.

The probe uses the existing shared C++ queue, deadline, cancellation, serial/identity and consent mechanisms. Only the fixed PAGE_SIZE read was added to ADB's command plan; `is-userspace` was already probed and is now rechecked for non-probe Fastboot operations. Production's compile-time write deny policy is unchanged. Exact command-plan tests reject shell text appended to the new query.

AR/EN UI and explicit JSON export project the native observation profile; raw outputs/serials/paths remain excluded from that compatibility projection. Android 15–17, future API, preview/missing/invalid data, unknown/duplicate/changed Fastboot mode and export behavior use synthetic fixtures. A normal API recognition label does not mean the device or operation is accepted.

## Physical acceptance still required

For each exact regional model, installed build and transport: record Platform-Tools version/hash, OEM driver/interface binding on Windows 10/11, ownership authorization, observed model/SoC/API/security patch and the complete operation evidence. Compare battery/storage/page-size observations with independent on-device results; exercise two-device ambiguity, disconnect, cancellation and timeout. Approve capabilities individually. Destructive/OEM tests require separate authorized Laboratory devices and verified postconditions; none are approved by this document or the catalog.
